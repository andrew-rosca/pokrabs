# POKRABS Implementation Progress Log

## Project Overview

POKRABS is a web application for hierarchical problem decomposition using the POKRABS framework (Problem → Objective → Key Results → Actions → Blockers → Status). The system recursively breaks down problems until actionable work is identified.

## Architecture Decisions

### Technology Stack
- **Frontend**: React 18+ with TypeScript
- **Backend**: Node.js with Express and TypeScript
- **Database**: SQLite (MVP), with abstraction layer for future PostgreSQL/MySQL support
- **Build Tool**: Vite for frontend (fast HMR, modern tooling)
- **Testing**: Vitest for unit tests, React Testing Library for component tests
- **Containerization**: Docker with single container for MVP

### Project Structure
- **Monorepo approach**: Separate `backend/` and `frontend/` directories
- **Shared types**: TypeScript interfaces/types shared between frontend and backend
- **API-first design**: All business logic implemented in backend API layer
- **Crisp architecture**: Clear separation between UI, API, and persistence layers

### Database Design
- **Repository pattern**: Abstract data access layer for testability and future database support
- **Migration system**: Schema versioning with migration files
- **Soft delete**: All deletions are soft (deletedAt field) to support future undo functionality
- **Hierarchical IDs**: Problems use parent chain IDs (e.g., "a2-df-7f") stored as strings
- **Data isolation**: All queries filter by workspaceId (and userId in Phase 2)

### ID Generation Strategy
- **LCG-based**: Linear Congruential Generator traverses ID space non-sequentially
- **Globally unique**: Single global counter ensures no duplicates across all entity types (problems, workspaces, views)
- **Non-sequential**: IDs appear random (e.g., i0, i5, na, xf) but deterministic
- **Full coverage**: Every ID in space generated exactly once before repeating
- **Expandable**: Automatically grows to 3-4 characters when space exhausted
- **O(1) generation**: No database lookups needed - just increment counter and apply LCG
- **Start offset**: Begins at middle of space (648/1296) for less predictable first IDs
- **Unified system**: All entities (problems, workspaces, views) use the same ID generation mechanism
- **Hierarchical**: Child problem IDs use same generation; hierarchy maintained via idPath field

### API Design
- **RESTful endpoints**: Standard CRUD operations for problems and projects
- **Special operations**: Dedicated endpoint for "decompose blocker" functionality
- **Error handling**: Consistent error response format
- **Validation**: Input validation on all endpoints
- **User isolation**: Prepare for Phase 2 authentication (user-scoped queries)

### Frontend Architecture
- **Component structure**: Modular, reusable components
- **State management**: React Context API or Zustand for global state
- **Routing**: React Router for deep linking to specific problems
- **Inline editing**: Table cells editable with auto-save on blur/Enter
- **Real-time updates**: Optimistic UI updates with server sync

### Testing Strategy
- **Unit tests**: Business logic, utilities, ID generation
- **Integration tests**: API endpoints, database operations
- **E2E tests**: Full user workflows (create problem, decompose blocker, etc.)
- **Test isolation**: Each test uses ephemeral database/data
- **TDD approach**: Write tests first, then implement functionality

### Development Workflow
- **Hot reload**: Fast development with HMR for both frontend and backend
- **Environment variables**: Separate configs for dev/test/prod
- **Docker support**: Single container for easy deployment
- **Database persistence**: SQLite file mounted as volume in Docker

### 2024-12-31 - LCG-Based ID Generator Implementation

**Completed:**
- **F011 (Updated)**: Implemented LCG-based ID generator
  - Replaced random ID generation with Linear Congruential Generator (LCG)
  - Uses formula: `next = (value * 37 + 5) mod space_size` for full period coverage
  - Global counter stored in `IdCounter` table (singleton pattern)
  - IDs start from middle of space (offset 648/1296) for less predictable first IDs
  - Automatic expansion to 3-char when 2-char space (1,296 IDs) is exhausted
  - All 1,296 two-character IDs generated exactly once before expansion
  - O(1) generation - no database uniqueness checks needed

**Database Changes:**
- Added `IdCounter` model to Prisma schema
- Migration: `20251231202955_add_id_counter` creates `id_counter` table
- Table stores: `id` (singleton key "global"), `counter` (current value), `length` (current ID length)

**Code Changes:**
- Created `backend/src/utils/id-generator.ts` with:
  - `generateProblemId()` - main ID generation function
  - `lcgNth()` - optimized LCG calculation with modular exponentiation for large n
  - `numberToBase36()` - converts numbers to base36 strings
  - `calculateSpaceSize()` - computes ID space size
  - `getIdCounterState()` - monitoring/debugging helper
  - `resetIdCounter()` - test utility
- Removed `generateChildProblemId()` - redundant wrapper, use `generateProblemId()` directly
- Removed `backend/src/utils/id-checker.ts` and tests - obsolete (LCG guarantees uniqueness)

**Testing:**
- 23 tests covering LCG math, ID generation, space expansion, full 2-char space uniqueness
- All tests pass (38 total across all utils)

**Technical Details:**
- LCG parameters: multiplier=37, increment=5 (satisfies full period requirements for base36)
- Initial offset: 648 (middle of 1,296 space) for less predictable first IDs
- Space sizes: 2-char=1,296, 3-char=46,656, 4-char=1,679,616
- Prisma 6 used (downgraded from 7 due to adapter configuration issues)

**Feature Details:**
- **Single caret (▸/▾)**: Toggles visibility of immediate children
  - ▾ (down arrow) indicates expanded state - children are visible
  - ▸ (right arrow) indicates collapsed state - children are hidden
- **Double caret (»/«)**: Expands/collapses entire descendant tree
  - » (double right arrow) expands all collapsed descendants
  - « (double left arrow) collapses all descendants that have children

- State is managed locally in React (not persisted to backend)

- Problem lookup uses idPath parsing for ancestor resolution

## 2025-01-02: Fixed Summary/Detail Cell Text Overlap and Jumping Issues

**Problem:**

**Root Causes:**

2. **Jumping Text**: The expanded and collapsed states used different positioning calculations that didn't account for the cell's padding consistently.

**Solution Implemented:**
1. Added `summaryRef` to measure the actual rendered height of the summary element
2. Added `summaryHeight` state to store the measured height
3. Added `wordBreak: 'break-word'` and `overflowWrap: 'anywhere'` to summary span for proper text wrapping
4. Updated the overflow detection logic to use measured summary height instead of constant
5. Fixed collapsed detail positioning to account for cell padding: `top: ${summaryHeight + 4}px` (4px = cell's top padding)
6. Ensured both states use consistent spacing: expanded uses `marginTop: 0.25rem`, collapsed uses `paddingTop: 0.25rem`
7. Added `opacity: 0.25` to collapsed detail so it's very dim and doesn't interfere with reading the summary

## 2026-01-05 - Deep Linking with Workspace, View, and Problem IDs

**Feature:** Enhanced deep linking to include workspace ID, view ID, and problem ID in URLs.

**Problem:**
The application previously supported deep linking to problems using only the problem ID (e.g., `/{problemId}`). However, to successfully share links, users needed to include the workspace ID and view ID context, as problems are workspace-scoped and views control which problems are visible.

**Solution:**
Implemented hierarchical URL structure with short prefixes that includes workspace, view, and problem IDs. All segments are optional, allowing flexible navigation.

**URL Structure:**
- `/w/{workspaceId}` - Workspace only
- `/w/{workspaceId}/v/{viewId}` - Workspace + View
- `/w/{workspaceId}/v/{viewId}/p/{problemId}` - Workspace + View + Problem

**Implementation:**

1. **Routing Updates (`frontend/src/App.tsx`):**
   - Refactored App component to separate `App` (BrowserRouter wrapper) and `AppContent` (routing logic)
   - Added routes for all URL patterns:
     - `/w/:workspaceId/v/:viewId/p/:problemId` (full path)
     - `/w/:workspaceId/v/:viewId` (workspace + view)
     - `/w/:workspaceId` (workspace only)
     - `/` (fallback)
   - Added `useParams` to read `workspaceId`, `viewId`, and `problemId` from URL
   - URL parameters sync to component state (`selectedWorkspaceId`, `selectedViewId`)

2. **State Synchronization:**
   - On mount, if URL contains `workspaceId`, it's used instead of auto-selecting first workspace
   - If URL contains `viewId` and it exists in the workspace, it's selected
   - If URL `viewId` is invalid or missing, default view is selected and URL is updated
   - When workspace is selected via UI, URL navigates to `/w/{workspaceId}`
   - When view is selected via UI, URL navigates to `/w/{workspaceId}/v/{viewId}` (preserving problemId if present)

3. **ProblemsList Updates (`frontend/src/components/ProblemsList.tsx`):**
   - Updated `useParams` to read from new route structure
   - Updated `handleCopyProblemUrl()` to generate URLs in format: `/w/{workspaceId}/v/{viewId}/p/{problemId}`
   - Updated `clearUrlIfDifferentProblem()` to preserve workspace/view segments when clearing problem
   - Problem navigation still works with new URL format (expands ancestors, scrolls to problem)

4. **Error Handling:**
   - Invalid `workspaceId` in URL → redirects to first available workspace
   - Invalid `viewId` in URL → selects default view and updates URL
   - Invalid `problemId` in URL → clears problem segment, keeps workspace/view
   - Missing segments handled gracefully (auto-selects defaults)

5. **Navigation Behavior:**
   - Workspace selection → navigates to `/w/{workspaceId}`, then auto-navigates to include default view
   - View selection → navigates to `/w/{workspaceId}/v/{viewId}`, preserves problemId if present
   - Problem link copy → includes all three IDs in URL
   - Action on different problem → clears problem segment, keeps workspace/view

**User Experience:**
- Shareable links include full context (workspace, view, problem)
- Browser back/forward buttons work correctly
- URL reflects current application state
- Invalid URLs automatically redirect to valid defaults
- Seamless navigation between workspaces, views, and problems

**Technical Decisions:**
1. **Short URL Prefixes**: Used `/w/`, `/v/`, `/p/` for brevity while maintaining readability
2. **Optional Segments**: All URL segments are optional, allowing flexible navigation patterns
3. **State-Driven Navigation**: URL updates when state changes via UI interactions
4. **URL-Driven State**: State updates when URL changes (browser navigation, direct links)
5. **Error Recovery**: Invalid IDs automatically redirect to valid defaults instead of showing errors

## Docker Image Size Optimization

**Date:** January 6, 2026  
**Status:** ✅ **COMPLETED**

### What Was Optimized

Reduced Docker backend image size by **55%** (1.33GB → 605MB) through multi-stage builds and eliminating unnecessary files.

### Image Size Results

#### Before Optimization
- **Backend:** 1.33GB
- **Frontend:** 81.4MB

#### After Optimization
- **Backend:** 605MB (55% reduction)
- **Frontend:** 81.4MB (unchanged)

### Key Optimizations

#### 1. Removed Prisma Query Engines (152MB saved)
- **Problem:** Entire `backend/prisma/` directory (152MB) was being copied, including query engines for all platforms (Windows, macOS, Linux x64, ARM, etc.)
- **Solution:** Only copy `schema.prisma` (5.5KB) and generate Prisma client in container
- **Result:** Only Alpine Linux binaries are generated, saving 152MB

#### 2. Multi-Stage Build (50MB+ saved)
- **Problem:** Build tools (`python3`, `make`, `g++`) remained in final image even though only needed during `npm ci` for compiling `better-sqlite3`
- **Solution:** Two-stage build:
  - **Stage 1 (builder):** Install build tools, compile native modules
  - **Stage 2 (production):** Copy only compiled dependencies, no build tools
- **Result:** Final image contains only runtime dependencies

#### 3. Added `.dockerignore`
- Excludes unnecessary files from Docker build context
- Reduces build time and context size
- Excludes: source files, tests, docs, IDE configs, Prisma generated files

### Technical Implementation

#### Multi-Stage Dockerfile Structure
```dockerfile
# Stage 1: Build dependencies (with build tools)
FROM node:20-alpine AS builder
RUN apk add --no-cache python3 make g++
RUN npm ci --production

# Stage 2: Production image (without build tools)
FROM node:20-alpine
COPY --from=builder /app/backend/node_modules ./node_modules
# Only copy schema.prisma, not entire prisma directory
COPY backend/prisma/schema.prisma ./prisma/schema.prisma
RUN npx prisma generate  # Generates only Alpine binaries
```

- `.dockerignore`: Created to exclude unnecessary files from build context

## Multi-Architecture Docker Image Support

**Date:** January 6, 2026  
**Status:** ✅ **COMPLETED**

### What Was Fixed

Fixed Docker images to support both x86 (amd64) and ARM64 architectures, ensuring images work on Intel/AMD processors as well as Apple Silicon and ARM servers.

### Problem

- **Issue:** Container images were built only for ARM64 (Apple Silicon)
- **Symptom:** Images failed on x86 machines with native module errors
- **Root Cause:** `better-sqlite3` native module was compiled only for ARM64 architecture

## Drag-and-Drop Parent Change Confirmation

**Date:** 2025-01-06

**Summary:**
Added a safety feature to prevent accidental parent changes when dragging and dropping problems. The system now distinguishes between reordering (same parent) and parent changes, requiring confirmation only for the latter.

**Features Implemented:**

1. **Parent Change Detection:**
   - Automatically detects when a drag-drop operation would change a problem's parent
   - Compares current `parentId` with the new `parentId` that would result from the drop
   - Only triggers confirmation when parent actually changes

2. **Confirmation Dialog:**
   - Modal dialog with backdrop overlay
   - Clear warning message: "This will move the problem and all its children to a different parent. Are you sure?"
   - Confirm (✔) and Cancel (✕) buttons
   - Escape key to cancel
   - Click outside dialog to cancel

3. **Seamless Reordering:**
   - When dragging within the same parent (reordering siblings), no confirmation is shown
   - Immediate execution for reordering operations
   - Maintains existing drag-and-drop functionality for same-parent moves

4. **User Experience:**
   - Drag state is maintained until user confirms or cancels
   - Visual feedback continues during confirmation
   - All children move with the parent when confirmed

**Technical Details:**
- Added `pendingMove` state to track moves requiring confirmation
- Modified `handleDrop` and `handleDropOnNewRow` to check for parent changes
- Created `executeMove` helper function to separate move logic from confirmation logic
- Used React Portal for modal dialog rendering (proper z-index handling)
- Added CSS styles for modal overlay and dialog

**Files Modified:**
- `frontend/src/components/ProblemsList.tsx` - Added parent change detection and confirmation dialog
- `frontend/src/index.css` - Added styles for parent change confirmation dialog

**Implementation Status:** ✅ **PARENT CHANGE CONFIRMATION COMPLETE**
